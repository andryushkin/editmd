# DeepSeek Q&A — 2026-07-08 11:02

**Project:** editmd (ios_swift)  
**Model:** deepseek-v4-pro  
**Context:** 5.3KB context injected

## Question

SwiftUI/AppKit Markdown-редактор (macOS). Диагностировал зависание при открытии больших .md. Файл: 342K символов / 1826 строк — это ОДНА гигантская GFM-таблица (~9000 ячеек, 5 колонок).

Замеры (release функций, без layout):
- collectSpans (подсветка Source, вызывается на КАЖДЫЙ keystroke синхронно): 276 ms
- lint (Source, дебаунс 0.3с + на открытии): 1207 ms
- renderMarkdownToAttributed (Visual, при открытии): БЫЛО зависание на минуты → стало 301 ms после того как я сделал struct MDBlock (значение атрибута NSAttributedString) Hashable вместо только Equatable. Runtime сам ругался: 'Obj-C -hash invoked on Swift value MDBlock that is Equatable but not Hashable; severe performance problems'.
- serialize attributed→markdown (Visual, на каждый keystroke): 128 ms

НО: эмпирически запустил app — в режиме Visual (дефолт) CPU держится 100% >30с даже после Hashable-фикса. Причина: TextKit LAYOUT из ~9000 NSTextTable-ячеек (isRichText=true, каждая ячейка = отдельный NSTextTableBlock). Render быстрый, но layout гигантской таблицы вешает. Source (plain text, без NSTextTable) такой файл раскладывает нормально.

Моё предлагаемое решение fix #1:
1. MDBlock: Hashable (уже сделал, убирает compute-зависание render/serialize).
2. Порог 'большой документ' = 100_000 UTF-16. Выше порога: принудительно effective mode = Source, и внутри Source — plain (пропустить collectSpans-подсветку И пропустить lint). Это гарантирует мгновенное открытие и отзывчивость. Дефолтный режим (Visual) сохраняется для нормальных файлов; для больших — только Source-plain.

Вопросы:
1. Слабые места такого подхода? Правильный ли порог 100K символов, или лучше считать по-другому (кол-во строк таблицы? наличие огромной таблицы? суммарный размер)?
2. Принудительная смена режима на Source для больших файлов (игнорируя сохранённый Visual) — это приемлемый UX или лучше не менять режим, а деградировать каждый режим отдельно? Учти что Visual для такого файла в принципе непригоден (layout вешает), а per-keystroke re-serialize всего документа O(n) тоже плох.
3. Не упускаю ли я более чистое решение (напр. ленивый/инкрементальный layout, лимит на размер таблицы, виртуализация)? Или для нишевого MD-редактора порог+плейн — прагматично достаточно?

Дай короткий критичный разбор, без воды.

## Answer

Твоё решение прагматичное и, как правило, достаточное для нишевого редактора. Ниже — сжатый разбор по трём вопросам.

### 1. Слабые места и выбор порога

**Порог на 100K UTF-16 — разумный, но не идеальный триггер.**  
Проблема именно в таблицах (NSTextTable), а не в общем размере. Возможны документы >100K без таблиц, которые нормально работают в Visual, и документы 80K с одной широкой таблицей, которые повесят.  
Лучше триггериться **по числу ячеек** (например, >2000 ячеек в таблицах). Определить это можно дешёво: посчитать строки, начинающиеся с `|`, или парсить таблицы в plain-режиме (без NSTextTable) и получить общее количество ячеек до построения attributed-строки. Если подсчёт ячеек дорогой, оставь общий порог символов, но понизь до 80K и добавляй проверку на наличие хотя бы одной таблицы (например, regex `^|.*|` по первым 500 строкам). Это снизит ложные срабатывания.

### 2. Принудительный Source vs. деградация каждого режима

**Принудительный Source — приемлемый и более безопасный UX**, чем деградация внутри Visual.  
Причина: Visual для мега-таблиц принципиально непригоден — даже с усечением layout остаётся экспоненциальным (TextKit с таблицами ведёт себя O(N²)). Source-plain (без подсветки и lint) даёт мгновенную отзывчивость.  
Чтобы не бесить пользователя, который привык к Visual, сделай одноразовое **уведомление внутри окна** (не модальное): «Документ содержит очень большую таблицу, для производительности открыт в исходном режиме. [Переключить в Visual (может подвисать)]». Кнопка переключения — сознательный выбор пользователя.  
Per-keystroke сериализацию для Visual в больших файлах ты отключишь самим фактом ухода в Source. Если позже пользователь принудительно переключится в Visual, сериализация всё равно останется O(n) — тут уже на его страх и риск.

### 3. Упущенные более чистые решения

Теоретически доступны, но для нишевого редактора **неоправданны**:

- **Виртуализация / ленивый лэйаут таблиц** — потребовал бы перехода на TextKit 2 (NSTextLayoutManager) и написание кастомных NSTextElements, что равноценно созданию собственного layout engine. Избыточно.
- **Замена огромной таблицы на placeholder в аttributted-строке** — сохранило бы Visual, но добавило бы сложности: нужно модифицировать парсер таблиц (вставлять свернутый блок с текстом «[Огромная таблица]»), отдельную сериализацию обратно и защиту от потери данных. Реализуемо, но ты потратишь неделю на угловые случаи.
- **Инкрементальная подсветка** (только видимый участок) — сложна, но может быть полезна отдельно для Source. Однако для первого быстрого открытия достаточно порогового plain.

**Резюме:** твой план «порог + Source-plain» — минимальное, достаточное и крайне быстрое в реализации решение. Добавь только эвристику по ячейкам таблицы и явный UI-сигнал, чтобы пользователь не думал, что программа сломалась. Минимизируй ложные срабатывания — и проблема закрыта.
